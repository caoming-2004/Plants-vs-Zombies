# 植物大战僵尸 Constitution

## Core Principles

### I. 完整可玩的核心循环优先

开发必须优先打通开始游戏、获取和消耗资源、种植防御、应对敌人、
明确的胜负结果及重新开始这一完整循环。
首个可玩版本必须覆盖上述流程，后续功能必须在保留该流程的基础上迭代。
装饰效果、额外内容和复杂系统不得优先于尚未完成的核心循环。
每个功能需求必须说明其对可玩体验的价值，并给出可观察的验收标准。
理由：完整的一轮体验才能验证玩法是否成立，为后续扩展提供基础。

### II. 游戏规则与界面渲染分离

资源计算、种植校验、伤害结算、敌人行为和胜负判定必须由游戏逻辑负责；
渲染负责展示状态，输入处理负责向游戏逻辑传递玩家操作。
同一规则必须有明确的权威实现，不得在界面和逻辑中重复维护判定。
核心规则必须能够在不依赖实际画面绘制的条件下验证。
按清晰的数据和调用边界划分职责，不强制特定框架或为每个概念建立独立模块。
理由：隔离表现变化对玩法的影响，便于验证与维护。

### III. 关键数值集中管理

影响玩法和平衡的数值必须在明确命名的配置或常量中统一管理，包括植物价格、
生命值、伤害、攻击间隔、移动速度、资源产出和波次参数。
同一含义的参数必须只有一个权威定义，使用处引用定义，不得散落重复的裸数值。
不同含义的参数即使当前取值相同，也不得仅因数值相同而合并。
配置必须明确参数含义及适用单位；含义明确且与玩法无关的局部数值不必集中。
理由：便于调整平衡，并避免多个位置取值不一致。

### IV. 核心玩法修改必须验证

修改资源、种植、战斗、敌人推进或胜负规则时，必须验证受影响行为，
覆盖正常路径、相关边界条件和失败路径，并记录执行方法、预期与实际结果。
可独立验证的规则优先采用自动化测试；涉及输入、渲染和游戏节奏的行为，
必须通过可重复的试玩步骤或相应集成验证确认。
验证规模必须与风险匹配，不要求所有改动都采用测试驱动开发。
失败、未执行或受环境阻碍的检查必须如实报告，不得把未验证行为标为通过。
理由：规则变化可能影响整轮结果，完成结论必须有实际证据。

### V. 新增功能保持已有功能可运行

新增功能必须识别受影响的已有行为，并执行相应回归检查。
已有可玩版本必须保持可启动、核心循环可完成、胜负反馈正确，
并确认重新开始后游戏状态重置；已知回归必须修复后才能宣称功能完成。
确需改变既有行为时，必须先明确需求变更的范围、原因与新验收标准，
同步相关方案、任务和验证依据，不得将意外破坏视为正常功能变化。
理由：保证迭代持续产生可用版本，避免功能增加而整体体验退化。

## 开发约束

- 技术方案必须服务于当前可玩目标，复用适用的现有结构；新增依赖或复杂抽象必须说明必要性。
- 设计必须明确游戏状态归属、规则与渲染边界，以及关键数值的配置位置。
- 首个版本仅要求足以验证完整循环的内容规模；具体植物数量和关卡范围由功能需求确定。
- 本宪章不预设语言、引擎、框架和具体平衡数值，技术选择在功能方案中记录。

## 开发流程与验收

1. 需求阶段明确玩家行为、范围和成功标准，优先安排可独立验收的可玩增量。
2. 方案阶段逐条检查五项原则，明确职责边界、参数管理和验证方法。
3. 任务阶段列明实现工作、必要的核心规则验证和受影响功能的回归检查。
4. 实现阶段按依赖推进，需求或方案改变时同步相关文档与任务。
5. 完成阶段核对验收标准，报告实际检查结果及遗留问题；任务勾选不能替代运行证据。

## Governance

本宪章是需求、方案、任务和代码审查的共同依据，各阶段必须检查适用原则。
出现冲突时必须先解决冲突，不得直接宣称符合本宪章。

修订必须记录原因、受影响原则、兼容性影响及必要的迁移或文档同步工作，
由项目维护者确认后生效；用户明确要求修订即构成本次修订的确认。
后续命令必须读取当前宪章，不得依赖旧对话中的规则副本。

版本采用语义化版本：删除或不兼容地重定义原则提升主版本；新增原则、章节或
实质性扩展约束提升次版本；不改变含义的澄清、措辞和错别字修正提升补丁版本。
本次首次正式制定，版本为 1.0.0，首次批准和最后修订日期均为 2026-10-25。
后续修订必须保留首次批准日期，更新最后修订日期，并使版本记录保持一致。
